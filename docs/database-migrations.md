Database Migration Workflow

Overview

This project is using Alembic for database migrations.

The migration files are present in:

alembic/versions/

Alembic configuration is present in:

alembic.ini

The database URL is taken from the "DATABASE_URL" configuration.

Basic Commands

Check current migration

To check which migration is currently applied:

alembic current

To check the migration heads:

alembic heads

To see the complete migration history:

alembic history

Create a Migration

After making a database model/schema change, a new migration can be generated using:

alembic revision --autogenerate -m "describe the change"

Example:

alembic revision --autogenerate -m "add candidate verification fields"

The generated migration should be checked before applying it. Only the required changes should be kept in the migration.

Apply Migration

To apply all pending migrations:

alembic upgrade head

After upgrading, check the current revision:

alembic current

Rollback Migration

A specific revision can be used for rollback:

alembic downgrade <revision>

For example:

alembic downgrade ba062b2def4d

This project has merge migrations, so:

alembic downgrade -1

can give an "Ambiguous walk" error at a merge point because there is more than one parent revision.

Using an explicit revision avoids this problem.

For example, we tested:

alembic downgrade ba062b2def4d

and the rollback completed successfully.

Upgrade After Rollback

After rolling back, migrations can be applied again using:

alembic upgrade head

This was also tested successfully.

Checking Model Changes

Alembic provides the following command to check whether the current models have changes compared with the database:

alembic check

At the time of this setup, "alembic check" reported some differences between the current SQLAlchemy models and the existing migration history.

These include additional tables, indexes, constraints and some column differences.

These differences were not added as a new migration because the task does not require converting existing manual schema changes into Alembic history.

Before creating an autogenerated migration, review the output of "alembic check" and make sure the changes are actually required.

Guidelines

- Create a new migration for new schema changes.
- Check autogenerated migration files before using them.
- Use "alembic upgrade head" to apply migrations.
- Use an explicit revision for rollback when dealing with merge points.
- Do not modify already applied migration files unless it is discussed with the team.
- Keep migration files inside "alembic/versions/".
- Do not commit database passwords or other secrets.

Testing Done

The migration workflow was tested on a clean PostgreSQL test database.

The following commands were run successfully:

alembic upgrade head
alembic current
alembic downgrade ba062b2def4d
alembic current
alembic upgrade head

After the final upgrade, the database was at:

a9c4c63a79be (head)

So the existing migration chain can be upgraded, rolled back to an explicit revision, and upgraded again.

## Production PostgreSQL & Managed Database (Neon) SSL Configuration

- Managed PostgreSQL (Neon): Managed cloud PostgreSQL requires SSL/TLS connections. Production should set `DATABASE_SSLMODE=require`.
- Required PostgreSQL environment variables: `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, and `DATABASE_SSLMODE=require` (or `DATABASE_URL` containing `sslmode=require`).
- Fail-Closed Policy: PostgreSQL connection or SSL configuration failures will propagate errors and fail closed. The application does not silently fall back to local SQLite when PostgreSQL is configured.
- Secret Hygiene: Never commit database credentials or connection strings.
